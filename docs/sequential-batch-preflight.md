# 同批次先调兵再部署：实施与验收

本轮修复 AI 顺序批次中，后续部署按批次开始时驻军被提前拒绝的问题。修改覆盖玩家 AI、专属势力 AI、世界 AI 批量指令，不改变单条战略校验和真实执行规则。

## 原因与方案

- **旧行为**：每条指令独立查询初始驻军。例如宜宾初始 5k，前序成都调入 15k；后续部署 15k 在调兵执行前就被预检删除。
- **依赖跟踪**：每个批次创建独立的 `createBatchTroopPreflight`，仅记录通过结构和战略预检的前序调兵目的城、征兵城市。按势力与解析后的城市编码隔离，中文名与编码指向相同城市。
- **延后检查**：对存在前序增兵依赖的城市，仅将后续驻军数量检查推迟到逐条实际执行前；不会预测前序一定成功，不会预支资源，不改变世界态。
- **执行边界**：调度器保持原顺序；`checkLiveOrder` 每条重读真实驻军、归属、路线、外交、银粮和行动点。依赖前序失败或被世界裁判过滤时，后续指令仍按实际状态检查，不会凭空部署；有足够原驻军的独立后续动作仍可执行。
- **仍然拒绝**：没有增兵前序的超量调兵/部署、敌方城市、系统专属操作、未选势力。拒绝的前序、结构错误、非有限或非正增兵量、同城调兵不会建立依赖；世界 AI 未知 actor 不进入预检。
- **不扩张权限**：混合 actor 批次共用顺序跟踪但按势力隔离；执行身份仍由可信编排器写入，而不是拿模型 JSON 提升权限。

这里的“预检通过”只表示进入后续裁判和执行，不承诺成功。即使增兵数量仍然不足，也由执行层确定性拒绝；未实现投影世界模拟或整批事务回滚。

## 回归覆盖

新增两份测试，扩充战略契约测试：

- **玩家与势力入口**：先调兵后部署、对象身份和顺序保持、预检不改状态、逆序仍拒绝、批次不串状态。
- **依赖资格**：敌方来源、超量来源、同城转移、非法数值、征兵后调兵、跨势力隔离、系统操作与空身份。
- **真实调度器**：15k 调入后部署、征兵后调出、显式战斗出兵、费用只扣一次、真实兵量守恒。
- **失败边界**：缺银、缺粮、不可达路线、前序被裁判过滤、归属变化、剩余行动点耗尽、重复部署超量。拒绝不扣费、不扣行动点、不改世界态，并有零消耗回执。
- **世界批量入口**：交错 actor 顺序不重排，后续部署使用可信身份入队；结构错误、未知 actor、敌方城操作不能解锁增兵依赖。

`tests/tacticalSetbackReplay.spec.ts` 的 run 2 现在显式验证修复后的执行差异。原 `docs/fixtures/tactical-setbacks.json` 完全保留，不将历史失败回执、战斗结算或服务中断改写为新成功样本；run 1、run 3 保持原始结果一致性检查。

## 历史计划的修复后离线结果

重用历史模型计划和相同初始状态，不发起新模型请求：

- **执行**：成都向宜宾调入 15k 成功，行军银 82.9、粮 62.1；随后宜宾部署 15k 成功，部署本身不另收银粮。
- **状态**：宜宾驻军 5k、外出部队 18k；剩余行动点 3，银 1109.9、粮 652.5。旧记录只有调兵成功，宜宾驻军 20k、外出部队 3k、剩余行动点 4。
- **回执**：按执行顺序生成两条成功回执，各消耗 1 行动点，不再生成旧的初始驻军战略拒绝。
- **边界**：修复后战斗结算会因部队不同而变化，不能拿旧结算做“相同战果”断言，也不算新的真实模型对局或连续受挫决策验证。
