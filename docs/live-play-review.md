# map-war 实机试玩与游戏性复评

本轮从用户已合并的主分支 `09704dc` 继续，实际进入川军、查看前线、输入自然语言指令，并调用 `step-5-preview` 执行征兵、出征和整合操作。我的主观判断仍是“有特色的策略原型”，游戏性约 **6.5/10**：路线、留守、补给和阶段提示已让选择更可信，但等待节奏、可见战役目标和持续敌方压力仍未证明成熟。这不是玩家留存研究或完整通关评分。（[项目仓库](https://github.com/ZhengHaoF/map-war)）

## 方法与边界

- **实际操作**：使用本地 Chromium，通过界面的输入框、按钮和存读档功能操作；没有直接修改 store 来制造试玩结果。状态通过只读钩子和只读检查获取，截图另行核对。
- **模型与后端**：模型使用用户指定的 `step-5-preview`。为安全使用已保存凭据，测试用本地隔离转发层替代 NestJS 的 HTTP 转发；前端、规则、战斗公式和 reducer 均为项目真实实现。不能据此声称生产 SDK 的认证配置也已验证。
- **输入兼容性**：本沙箱原生指针/键盘输入此前存在不稳定现象，本次按钮以 DOM click 事件触发，文字通过输入框填入。它验证 UI 事件链与实际规则，不等于覆盖真实设备的完整鼠标、触屏和键盘手感。
- **排除项**：初次转发配置错误导致一次认证失败；初版测试转发层的 4096 输出上限导致两份世界决策返回空正文和 `finish_reason=length`。这些不计作模型非法指令或游戏 AI 策略失败；后续输出上限提高到 16384。
- **临时测试会话**：续玩期间测试转发会话到期，部分请求返回 `invalid or expired session token`。刷新转发会话后，直接探针和后续实机调用恢复成功；这些失败也不计作模型计划的有效性样本。
- **样本限制**：这是单势力、短时、开局样本，不是 40 回合实机对战。上一轮 40 回合数据仍然是脚本基准，本轮保留的真实回复离线重放也不能重复计作实玩局数。
- **故障现场续玩**：通过游戏保存/读取界面保留现场，在修复版本继续操作。故障回合已经结算经济但没有推进日期，后续续玩又进行了一次结算；因此本局不能用于标准回合经济比较，修复也不自动重写旧存档。

## 亲自玩到的选择

- **先征兵再出征**：宜宾原驻军 8k；输入“先征兵 2k，再派 6k 攻昭通，至少留 2k”后，两条指令按顺序成功。宜宾实际留 4k，银从 1200 降至 1181.6，粮从 720 降至 707.2，行动点从 6 降至 4。
- **出征前可理解的代价**：前线界面显示宜宾到昭通约 120km、补给通畅、参战 6k，预计消耗银 14.4、粮 10.8 和 1 行动点。该成本与实际扣款一致，不再只是依赖一句“可以进攻”。
- **占领后整合**：真实结算中双方各损 1k，昭通以川军 5k 驻军完成占领并进入整合期；随后要求昭通整军 10、筑防 5，再在宜宾征兵 2k，三条均成功。阶段提示依次出现“支援战线”和“整合”，能引导下一步而不强制代替玩家决策。
- **守城与继续扩张的机会成本**：上述整合批次实耗银 11.5、粮 2、3 行动点。由于首次日期推进故障未恢复行动点，它实际仍发生在第 0 回合，不能把它描述为一个正常的新回合。
- **修复后真实回合推进**：读档续玩后，世界批量模型返回的 25 条征兵/筑防在 UI 中实际执行，25 份执行回执均成功。日期实际变为 `1931-04-08`、回合数变为 1、川军行动点恢复至 6；不只是看到“回合结束”提示。
- **新回合再次整备**：最后要求昭通筑防 3、整军 5，两条均实际成功，实耗银 4.5、不耗粮、行动点从 6 变为 4。最终银 1182.2、粮 1081.7，昭通工事 28；新增 UI 成功结果显示实际成本。
- **敌方决策未完整通过**：关联的滇系调用连续三次收到上游 `502 / upstream request failed`，这一阶段最终未取得可用决策。不能把滇系没有反击解释成 AI 故意保守；其他势力 25 条内政成功也不能代替敌方军事能力验证。

## 发现并修复的问题

### 回合提示与实际日期脱节

首次结束回合后，界面提示推进至 `1931-04-08`，但实际日期仍为 `1931-04-01`、回合数仍为 0、行动点也未恢复。源码中云雾回调要求动画帧恰好落在停顿区间，掉帧或后台节流跳过该区间就会漏掉推进。

修复包含两层保护：云雾在越过遮罩阈值后保证触发一次；系统时间推进在演出结束后另作幂等兜底，不能只宣布一个没有提交的日期。新回归先在旧代码上复现 2200ms 和 4000ms 跨帧失败，再验证修复；同时覆盖普通动画以及中段回调完全未触发的降级路径。（[项目实现](https://github.com/ZhengHaoF/map-war)）

### AI 记得叙事，却可能忘记失败

原玩家多轮上下文会去掉执行成功/失败标记，且没有带入完整校验摘要和拒绝原因；调度器结果也只保存在运行时。因此模型可能继续相信“已经开拔”等叙事，或不知道上条计划为何失败。

本轮新增只读、可存档的执行层回执，记录真实调用方身份、结果、原因、实际行动点和银粮变化，以及剩余预算。后续玩家上下文保留失败标记与拒绝原因；势力历史只读取本方回执，并明确执行回执优先于模型叙事。常规回执保留在日志，不重复塞进回合大事记。（[项目实现](https://github.com/ZhengHaoF/map-war)）

这没有取消现有逐条执行语义：前面成功的行动保留，后面预算不足的行动被拒绝，不自动回滚整批。异常情况下若银粮已经扣除，回执会反映实际变化，而不是谎称“失败所以没有扣款”；完整动画事务回滚仍是未完成的工程项。

### 请求失败不可读、输入被清空

实机请求失败时，界面出现 `[object Object]`，原始指令也被清空。本轮将嵌套错误结构规范化为可读提示，并在请求或解析失败后保留输入，不追加空的“已完成”对话轮。

另用一次隔离的 UI `502` 故障注入验证：提示变为“模型服务暂未响应（HTTP 502），请稍后重试”，输入仍保留，游戏状态完全未变。该故障注入不是额外的真实模型请求，也不加入模型无效指令率统计。

## 游戏性判断

- **已改善：战术意图更容易落地**。征兵、留守、出征顺序和银粮成本能产生真实结果；前线预览能回答“从哪里打、付出多少”，地图比最初评估时更有策略意义。
- **仍偏弱：短期目标多靠玩家自定**。这次目标“夺昭通并整合”是我自己提出的，不是游戏提供的战役任务。阶段提示有帮助，但不是可见进度、完成条件和奖励构成的完整目标链。
- **仍偏弱：初始驻军差异和压力**。本次昭通只有 1k 守军，6k 进攻一轮拿下，不能证明敌方能持续组织反击或形成中盘张力。城市与势力经济差异仍需更长局验证。
- **优先改善：等待与信息噪音**。世界模型调用及大量常规内政的串行演出会打断玩家决策。沙箱渲染性能、转发层和上游失败会放大等待，不能直接推导所有玩家的延迟；但每条日常内政都做镜头演出的设计本身值得提供快速模式。
- **优先改善：大事记聚焦**。本次修复后回合摘要仍列出 47 条经济、25 条内政和 25 条行动点事件，玩家很难快速找到真正影响自己决策的变化。建议合并例行支出、突出本方与关联前线，并默认折叠其他势力内政，而不是仅加入更多日志。
- **暂不下结论：外交和多战线耐玩性**。这轮未完整体验外交交换、围攻与多战线长期维护，不把源码存在这些功能当作实机验证完成。

测试转发层记录的三次成功玩家请求耗时约 11.4、14.2 和 21.9 秒，成功世界批量请求约 45.8 秒；这些只计服务响应，不含动画和输入等待。样本太小、运行条件特殊，不用于承诺普遍延迟，但足以说明当前体验需要认真处理等待节奏。

## 下一步建议

先把“西南短战役”做成小而完整的目标链：取得一个边境支点、保住补给连接、完成整合并守住若干回合，显示明确的完成条件与进度。它应复用现有路线和补给规则，而不是再引入复杂交通网络；同时为世界日常内政提供快速结算，保留关键战斗演出。

之后组织不熟悉项目的玩家测试“第一次有效行动、能否解释一次输赢、是否知道下一步目标”和一局 10 至 15 回合体验。不要先加科技树、更多指令或全国规模任务来掩盖基础节奏问题。

完整回归 34 个文件、407 个测试通过，包含 6 份较早的真实回复重放、本次真实批次的两项离线回归，以及动作累计银粮和第七条行动被拒绝的测试。脱敏 fixture 保存 3 份玩家回复和 1 份世界批量回复；成功操作样本共 32 条，但没有可用的真实非法计划样本，不能据此宣布模型规划普遍可靠。离线回归使用替代动画，不能代替 UI 掉帧测试；本次掉帧另有明确的失败前后证据。

前端类型检查、前后端构建通过。ESLint 仅检查 JavaScript，配置本来就忽略 TypeScript/Vue；Oxlint 仍有 41 个既存错误，本轮未新增，不宣称整个仓库 lint 干净。主包约 780.97kB、gzip 229.41kB，仍有体积告警；完整动画事务回滚、通用虚拟时间浏览器 helper 的既存失败和长期模型对战都没有在本轮解决。

成功状态的桌面 1440×1000、手机 375×812 截图以及手机错误截图均已检查，手机输入、行动按钮、实耗与错误提示可见，没有发现新增横向溢出或页面异常。该结果不推翻既有的通用虚拟时间 helper 失败，也不证明全部原生输入兼容性。
