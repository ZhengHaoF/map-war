## 一、产品定位与愿景

以 **1931 年九一八事变前后**为背景的中国战争策略推演游戏。

- **玩家 = 政权领袖**：发号施令 → AI 解析并落地操作 → 计为一回合；玩家无操作时也可**快进**，由 AI 自动推演战局。
- **系统只喂数据，AI 只产出意图**：引擎将当前世界态喂给 AI，AI 返回"下一步想做什么"（结构化指令），**不直接改写世界**——世界态只能由内核（Kernel）按事件确定性变更。
- **多 AI 势力同台演化**：玩家与若干 AI 政权、一个"世界 AI"在同一套规则下自主演化。
- 三种目标用法：
  1. **人机对战**：玩家操控一个政权，其余由 AI 推演。
  2. **全 AI 推演**：玩家只观察，AI 之间自主开战、合纵连横。
  3. **逐步喂数据观察**：手动逐事件推进，研究局势走向。

## 二、时空背景与剧本

- **时间起点**：`1931-04-01`（全局日期时钟，无回合制）。
- **地图范围**：中国全境约 **380 座城市**（GeoJSON 要素，含行政编码 `gb`、名称、经纬度），以 **Leaflet 为底图引擎 + PixiJS 动画叠加层** 的混合架构渲染。
- **世界背景层**：若干列强国家（日本、苏联、美、英、法等）作为地缘政治背景，影响外交与威胁评估，不直接参与内战地图的占领。
- **可选剧本**：设计上预留 `1931 / 1937 / 1941 / 1945` 多剧本切换，开局种子（城市归属、驻军、士气）随剧本不同。当前实现以 1931 为基线。

开局玩家从下列政权择一，其余交由 AI（或中立）。每个政权带"首都、领袖、兵力、定位"四要素，是 AI 战略推断与玩家代入的锚点。

## 四、地图与城市模型

### 4.1 设计理念：城市 = 战略节点

城市是整个游戏的**战略节点（Strategic Node）**，只保存**长期稳定且具有战略价值**的数据；动态数据交由其它系统维护。好处：数据清晰、AI 易算、剧本易做、后期易扩展。

| 城市保存（静态/半静态） | 不保存在城市（动态，由系统维护） |
|----------|----------|
| 地形、工业、粮食、城市规模、工事 | 补给、天气 |
| 行政编码、名称、初始归属 | 占领进度、建筑施工、战斗状态 |
| 驻军、外出兵力、士气（权威存储在城市，见 §5.1） | — |

> 注：驻军 `troops`、外出兵力 `fieldForce` 与城市士气 `morale` 虽随战事变动，但**权威存储仍落在城市级**（见 §5.1），衍生出"势力总兵力/总士气"等聚合值，不单独另存。

### 4.2 城市数据模型（字段规范）

| 字段 | 含义 | 范围 | 说明 |
|------|------|------|------|
| `gb` | 行政区编码 | 唯一 ID | 城市唯一标识，与 GeoJSON 要素对应 |
| `name` | 城市名称 | 文本 | 中文名，AI 可用地名直接指代 |
| `owner` | 当前实际控制政权 | 政权枚举 | 开局由剧本种子灌溉；运行中只经内核事件变更 |
| `terrain` | 地形 | 平原/丘陵/山地/森林/城市 | 影响行军、攻防、AI 寻路 |
| `cityLevel` | 城市规模 | 1~5 | 人口/经济/政治/交通综合评价 |
| `industry` | 工业能力 | 0~10 | 军工潜力，影响生产、恢复、AI 价值 |
| `food` | 粮食生产能力 | 0~10 | 征兵效率、恢复、AI 价值 |
| `fort` | 工事等级 | 0~5 | 天然防御 + 已有防御设施 |
| `troops` | 驻军 | 千（k） | 在城内的兵力；城市级权威存储 |
| `fieldForce` | 外出兵力 | 千（k） | 该城派出、正在外作战的兵力；开局全部为 0 |
| `morale` | 城市士气 | 0~100 | 城市级；势力士气为按兵力加权的各城均值（派生） |

> **驻军 vs 外出兵力**：出兵攻城时，兵力从 `troops` 转入 `fieldForce`（人真的离开了城市）。交战损耗从 `fieldForce` 扣（攻方）和 `troops` 扣（守方）。详见 §5.2。

### 4.3 地形与战斗修正

地形同时影响**行军速度、攻防系数、AI 战略价值**。推荐修正：

| 地形 | 攻击 | 防御 | 行军 |
|------|------|------|------|
| 平原 | 100% | 100% | 100% |
| 丘陵 | 90% | 120% | 90% |
| 山地 | 70% | 150% | 60% |
| 森林 | 80% | 130% | 70% |
| 城市 | 90% | 140% | 80% |

### 4.4 城市规模 / 工业 / 粮食 / 工事（评分标准）

**城市规模 `cityLevel`（1~5）**：人口、经济、政治影响力、交通地位的综合评价（非纯人口）。

| 等级 | 类型 | 参考 |
|------|------|------|
| 1 | 县城、小城 | 阿坝 |
| 2 | 普通城市 | 桂林 |
| 3 | 区域中心 | 长沙、南昌、济南 |
| 4 | 全国重要城市 | 武汉、广州、重庆、天津 |
| 5 | 超级城市 | 上海、北京、南京 |

**工业 `industry`（0~10）**：军工与工业基础。参考：上海 10、天津/沈阳 8、武汉 7、广州 6、长沙 4、瑞金 1。影响武器生产、城市恢复、AI 优先占领度。

**粮食 `food`（0~10）**：生产能力（非库存）。参考：开封 10、郑州/武汉/成都 9、长沙 7、广州 5、上海 2。影响征兵效率、部队恢复、AI 建补给中心意愿。

**工事 `fort`（0~5）**：天然防御 + 已有设施。参考：重庆 5、兰州 4、太原/西安 3、长沙 2、上海 1。玩家可继续修筑。

### 4.5 城市邻接图（硬需求）

从 GeoJSON 邻近关系**预计算**的城市邻接图，是多项机制的共同依赖：

- **士气孤立惩罚**：被敌方包围的城市士气额外下降（由邻接图派生，不依赖独立补给系统）。
- **AI 可达性判断**：行军路线经过哪些势力、有无天然屏障（秦岭、长江、大漠）。
- **快照瘦身**：AI 上下文只喂"周边若干跳 + 与上帧差异"，砍 token（见 §7）。

## 五、核心机制

### 5.0 世界态事件总览（14 种）

所有世界态变更（城市归属、兵力、士气、日期、势力存亡等）都必须封装为 `GameEvent`，由 Kernel（`applyEvent`）确定性地 apply——这是世界态的**唯一写者**。事件日志同时也是存档/重放的载体（见 §九）。

| # | 事件类型 | 类别 | 语义 | 关键字段 |
|---|---------|------|------|---------|
| 1 | `capture` | 世界态 | 占领城市：易主 + 可选写入新驻军 | `targetGb` `actor` `resultTroops?` |
| 2 | `moveTroops` | 世界态 | 调兵：从 A 城搬运 N 千兵到 B 城 | `fromGb` `toGb` `amount` |
| 3 | `deploy` | 世界态 | 出兵：驻军转为外出兵力（人离开城市） | `fromGb` `amount` |
| 4 | `reinforce` | 世界态 | 增援：向前线补充兵力 | `gb` `amount` `side: 'attacker'\|'defender'` |
| 5 | `attack` | 世界态 | 战斗损耗：攻方扣 fieldForce、守方扣 troops | `fromGb` `targetGb` `attackerLoss` `defenderLoss` |
| 6 | `moraleChange` | 世界态 | 士气增减（胜升/败降/被孤立惩罚） | `targetGb` `delta` |
| 7 | `cityStatChange` | 世界态 | 城市数值增减（工业/粮食/工事/规模） | `targetGb` `field` `delta` |
| 8 | `produce` | 世界态 | 生产/征兵：城市驻军增加 | `targetGb` `amount` |
| 9 | `dateAdvance` | 世界态 | 推进全局日期 | `date` |
| 10 | `setFactionAlive` | 世界态 | 设置势力存亡（灭亡则移出存活列表） | `faction` `alive` |
| 11 | `battleStart` | 战斗生命周期 | 战斗开始，登记元数据（含攻守方、回合数） | `battleId` `fromGb` `targetGb` `attacker` `defender` `fromName` `toName` |
| 12 | `battleEnd` | 战斗生命周期 | 战斗结束，携带终止原因 | `battleId` `reason: 'capture'\|'attackerRouted'\|'retreat'` |
| 13 | `selectFaction` | 玩家身份 | 选择玩家操控势力 | `faction` `playerName` |
| 14 | `narrative` | 叙事记录 | 玩家输入 + AI 总结文案，仅记录不改态 | `playerInput` `aiMessage` `kind?` |

> 说明：`battle`（指令）与 `attack`（事件）的关系——`battle` 是演出层指令（开启持续交火动画 + 登记 `battleStart` 事件），每回合真正的扣兵走 `attack` 事件，占领走 `capture` 事件。`deploy` 是开战前置（出兵），`reinforce` 是战斗中增援。

### 5.1 兵力与士气（城市级 + 派生聚合）

> 订正原则：兵力**权威存储于城市**，势力总兵力为派生值，绝不单独存储。

- **驻军 `troops`**：每城持有的在城兵力（单位千/k）。
  - 初始值：取史料势力总数 → 按城市权重（`cityLevel × industry`，首都加权）分摊到各城，一次性算进种子。
- **外出兵力 `fieldForce`**：每城派出的、正在外作战的兵力（单位千/k）。
  - 开局全部为 0（没有人在外面打仗）。
  - 出兵时从 `troops` 转入（见 §5.2 deploy 事件）；战斗损耗从此扣（攻方）；战斗结束按结果转回或清零。
- **势力总兵力** = Σ（该势力所辖城市 `troops + fieldForce`）（派生，归属变化或战斗损耗时重求和）。
- **士气 `morale`**：每城 0~100。
  - 势力士气 = 按各城 `troops` 加权的 `morale` 均值（派生）。
  - 初始：史料关键词 → 势力 base（如 CCP 高、SCC 低）→ 落到每城 `base + 首都加权(+8) + 城级修正((cityLevel−3)×3)`，clamp 20~100。
  - 驱动：所属势力胜↑ / 败↓ / 丢核心城(首都)↓↓ + 被孤立惩罚。

> **AI 上下文展示**：喂给 AI 的城市快照同时展示两个数——`奉天: 驻军 3000 | 外出 12000（正在攻锦州）`，让 AI 能判断"家里空不空、前线吃不吃紧"。

### 5.2 战斗系统（跨回合、AI 裁定、replay 安全）

战斗是本游戏的核心机制，采用**跨回合持续交战**模型——不是一回合投骰子出结果，而是多回合拉锯消耗，每回合都有决策空间。

#### 5.2.1 战斗状态机

```
PENDING ─→ ACTIVE ─→ RESOLVED
 (出兵)    (交战中)   (已结束)
```

- **PENDING → ACTIVE**：攻方从来源城派出 `fieldForce`（`deploy` 事件），`battleStart` 登记战斗元数据，动画启动。
- **ACTIVE**：每回合 P4a 自动结算一轮损耗（`attack` 事件扣双方兵），战斗持续播放动画。
- **RESOLVED**：满足终止条件 → 停动画 → `battleEnd`（带 reason）→ 出最终战报。

#### 5.2.2 开战：出兵（deploy）

攻方从来源城调兵出征，兵力从 `troops` 转入 `fieldForce`（人真的离开了城市）：

```
deploy 事件：
  fromGb: 来源城（如奉天）
  amount: 出征兵力（如 12000）
  效果：from.troops -= amount, from.fieldForce += amount
```

> 出兵后奉天驻军从 15000 降到 3000，外出兵力 12000。这 12000 人在外面打仗，不在城里。

**约束**：
- 一个城同一时间只能作为**一个方向**的攻方来源（`fieldForce` 是单一数值，不区分多路出击）。想两路出击？从两个城分别出兵。
- 出征兵力不得超过当前 `troops`。

#### 5.2.3 交战：每回合结算（P4a 战斗裁决 AI）

每回合推进时，P4a 战斗裁决 AI 对所有 ACTIVE 战斗裁定本轮损耗：

```
attack 事件（每回合每场战斗一条）：
  fromGb: 攻方来源城
  targetGb: 守方城市
  attackerLoss: 攻方本轮损耗（从 fieldForce 扣）
  defenderLoss: 守方本轮损耗（从 troops 扣）
  效果：
    from.fieldForce = max(0, from.fieldForce - attackerLoss)
    target.troops = max(0, target.troops - defenderLoss)
```

**AI 裁定 + 参考区间**：损耗由 AI 看战况裁定（弱策略推演，不需要确定性公式），但 prompt 里给参考区间防止离谱：

```
战斗损耗参考（AI 在此区间内自由裁定）：
- 攻守兵力相当 → 双方各损兵力的 8-15%
- 攻方 2:1 优势 → 攻损 3-8%，守损 10-20%
- 守方有工事(fort≥3) → 攻损额外 +20-40%
- 守方士气 < 30 → 守损额外 +30-50%
```

**地形修正**（§4.3 的表在此生效）：守方防御系数受 `terrain` 影响（山地 150%、城市 140% 等），作为 AI 裁定的参考输入。

**兜底公式**（仅 AI 挂了/漏了某场战斗时用，不是常态）：

```
fallbackTick(atk, def, fort):
  ratio = atk / max(def, 1)
  baseRate = 0.06
  attackerLoss = max(1, round(atk × baseRate × (1 + fort × 0.1)))
  defenderLoss = max(1, round(def × baseRate × ratio))
```

#### 5.2.4 增援（reinforce）

战斗进行中，任何一方可向战场增兵：

```
reinforce 事件：
  gb: 目标城市（攻方来源城 或 守方城市）
  amount: 增援兵力
  side: 'attacker' | 'defender'
  效果：
    attacker → from.fieldForce += amount（前线部队得到补充）
    defender → target.troops += amount（守城部队得到补充）
```

> 增援是"往前线送人"，不需要先进城再出城。AI 在 P3 决策时可以直接下 `reinforce`。

#### 5.2.5 终止条件与结算

战斗结束有三种情况，由 `battleEnd` 事件携带 `reason`：

| reason | 触发条件 | 结算 |
|--------|---------|------|
| `capture` | 守方城市 `troops = 0`（**唯一强制终止**） | 城市易主（`capture` 事件）；攻方剩余 `fieldForce` 转入被占城 `troops`（占领军）；来源城 `fieldForce` 清零 |
| `attackerRouted` | 攻方 `fieldForce = 0`，**或**来源城被第三方占领 | 战斗结束，攻方 `fieldForce` 清零；来源城若仍属攻方则无变化 |
| `retreat` | 攻方主动撤退（玩家/AI 下 `stopBattle`） | 攻方剩余 `fieldForce` 转回来源城 `troops`（人回来了）；不占领 |

> **唯一强制终止条件**：守方城市 `troops = 0`（占领）或攻方 `fieldForce = 0`（打光了）。其他情况全靠玩家/AI 每回合自主决策——继续打、增援、撤退、外交斡旋、投降，都是合法操作。

> **投降/放弃**（预留）：当前用 `stopBattle(reason:'retreat')` + `capture` 两步表达。后期可新增 `surrender` 语义。

#### 5.2.6 偷家（来源城被占）

攻方 `fieldForce` 在外面打仗时，来源城被第三方占领：

- 来源城易主 → 攻方在外兵力成为"无主之军"
- **自动触发 `attackerRouted`**：战斗终止，`fieldForce` 清零（溃散）
- 代码层检查：每回合结算时 `cities[from].owner !== attacker` → 强制结束

> 这是 `fieldForce` 拆分的自然推论——城没了，外面的人就散了。不需要额外规则。

#### 5.2.7 占领与攻克的衔接

```
守方 troops = 0
  → applyEvent('capture', { targetGb, actor, resultTroops: 攻方剩余 fieldForce })
  → applyEvent('battleEnd', { battleId, reason: 'capture' })
  → 攻方来源城 fieldForce 清零
  → 世界 AI 生成叙事 + 战场电报
```

> `capture` 的 `resultTroops` 自然就是攻方打完后剩下的兵——不需要额外计算。

#### 5.2.8 战斗时间线示例

```
1931年9月18日 (第1回合)
  玩家: deploy 奉天 12000（奉天 troops 15000→3000, fieldForce 0→12000）
  玩家: battle 奉天→锦州（动画开打，battleStart 登记）
  P4a 结算：攻损 400（fieldForce 12000→11600），守损 300（troops 8000→7700）
  电报(私信): "奉天出兵，锦州初战，东北军据城顽抗"

1931年10月2日 (第2回合)
  P4a 结算：攻损 500（fieldForce→11100），守损 450（troops→7250）
  电报(私信): "锦州外围据点被突破，守军退入城内"
  阎锡山电报来问: "需要援军吗？"

1931年10月16日 (第3回合)
  玩家: reinforce 奉天 3000（增援前线，fieldForce 11100→14100）
  P4a 结算：攻损 300（fieldForce→13800），守损 200（troops→7050）
  玩家可选择继续/加码/撤退

1931年11月1日 (第4回合)
  P4a 结算：守方 troops 只剩 800，归零
  → capture: 锦州易主，攻方剩余 fieldForce 13500 转入锦州 troops
  → 奉天 fieldForce 清零
  → battleEnd(reason:'capture')
  电报(世界): "锦州失守！东北军退守山海关"
```

#### 5.2.9 确定性红线（不变）

- **裁定结果必须写回事件本身**：`attackerLoss` / `defenderLoss` / `resultTroops` 均由 AI 裁定后写入 `attack` / `capture` 事件。
- **replay 不重跑 AI**：读档重放时，直接按事件中的数值扣兵，不再调用 LLM。
- **AI 只产出意图**：AI 不直接改世界态，所有变更经 Kernel `applyEvent` 落地。

### 5.3 生产 / 征兵

- **`produce` 事件**：城市驻军 `+amount`（k），代表征兵/军工产出。
- 玩家与 AI 均可经指令触发；是兵力随回合恢复的主要途径。

### 5.4 补给

- **v1 不加补给系统**。远程奔袭的"必败感"由**兵力差 + 地形 + 邻接孤立惩罚**隐含表达，避免早期规则膨胀。

### 5.5 战略价值（attackScore）

为规则 AI 兜底与 AI 优先级提供统一量纲：

```
战略价值 = cityLevel × 3 + industry × 2 + food − fort
```

数值越高越值得进攻。例：上海 `5×3 + 10×2 + 2 − 1 = 36`，长沙 `3×3 + 4×2 + 7 − 2 = 22`，AI 优先进攻上海。所有城市字段都必须**直接参与 AI 决策**（工业高→优先占、粮食高→建补给中心、工事高→绕路或集兵、规模高→死守）。

### 5.6 议和系统（Peace Negotiation）

战斗进行中，参战任何一方（攻方或守方）可主动发起**议和**。议和不是单方撤退——它需要**对方同意**，且对方可以**开出条件**。这是战斗系统中"打不下去就谈"的外交出口。

#### 5.6.1 触发与权限

- **攻方玩家**：战斗面板 / 战况浮层卡中显示「求和」按钮。
- **守方玩家**：同样显示（城被围攻，守方也可以求和——承认打不过，请求停战）。
- **旁观者**（非参战方）：不显示求和按钮。
- **AI 势力**：P3 决策阶段可自主发起议和（预留，v1 仅玩家可触发）。

#### 5.6.2 流程总览

```
玩家点「求和」→ 按钮"对方思考中…"
  → invokePeaceJudgment(...)          ← 1 次 LLM（对方领袖裁定）
  → 议和弹窗（GameModal, parchment）
      标题："议和 · {对方领袖}"
      内容：AI 半文言回应
      条件列表（若有）：割城 / 让兵
      按钮：[接受] [拒绝]
  → 接受 → 执行条件 → battleEnd(reason:'peace') → Toast
  → 拒绝 → 关闭弹窗 → Toast "议和破裂，战火重燃" → 战斗继续
```

#### 5.6.3 AI 裁定（对方领袖视角）

AI 扮演**对方阵营领袖**，以性格与战况为依据，决定是否接受议和、是否附加条件。

**输入**：

| 字段 | 来源 |
|------|------|
| 对方势力标签 / 领袖 / 性格 | `OWNER_DETAILS[defender]`（或 attacker，取决于谁是对方） |
| 攻方野战兵 / 守方驻军 | `atkForce(b)` / `defForce(b)` |
| 已战回合 / 上回合损耗 | `BattleInfo.turns` / `lastAttackerLoss` / `lastDefenderLoss` |
| 攻方城池列表（供割城条件选择） | `store.factionCities(attacker)` 前线城市 |
| 玩家身份 | `buildPlayerProfile()` |

**输出**（结构化 JSON）：

```json
{
  "accepted": true,
  "conditions": [
    { "type": "cedeCity", "city": "汉中市" },
    { "type": "cedeTroops", "city": "成都市", "amount": 10 }
  ],
  "narrative": "30-80字半文言回应（可放狠话、可慨叹、可勉允）",
  "reason": "一句话决策理由（给系统看）"
}
```

**AI 决策指引（写入 prompt）**：

- 兵力占优、士气正盛 → 可拒绝，或提出苛刻条件（割城 + 让兵）
- 势均力敌、久战疲敝 → 可接受，条件从宽（仅让兵少量）
- 兵力劣势、城防将破 → 应接受，无条件或象征性条件
- 性格影响：暴烈者多拒绝或狮子大开口；持重者多务实接受
- **条件须合理**：不得索要对方首都；让兵不得超过对方实际兵力；割城最多 1~2 座（前线小城）

**兜底**（AI 挂了 / 解析失败）：`{ accepted: true, conditions: [], narrative: '……' }`——默认无条件接受，不卡玩家。

#### 5.6.4 条件类型

| 条件类型 | 语义 | 落地事件 | 前置依赖 |
|---------|------|---------|---------|
| **割城** `cedeCity` | 求和方将一座城让给对方 | `capture`（actor = 对方势力） | 无（现有事件） |
| **让兵** `cedeTroops` | 求和方从指定城拨出 N k 兵力交给对方 | `transferTroops`（**新事件**） | 需新增事件类型 |
| **赔款** `reparations` | 求和方支付军费赔偿 | 待定 | **需国库系统**（v1 不具备） |

> **v1 实现范围**：割城 + 让兵。赔款留到国库系统落地后再接入。

#### 5.6.5 新增事件：`transferTroops`

跨势力兵力交接（区别于 `moveTroops` 的同势力内部调兵）：

```ts
| { type: 'transferTroops'; fromGb: string; toGb: string; amount: number }
```

**效果**：
```
from = cities[fromGb]   // 求和方的城
to   = cities[toGb]     // 对方的城
loss = min(amount, from.troops)
from.troops -= loss
to.troops   += loss
```

**约束**：
- `fromGb` 必须属于求和方；`toGb` 必须属于对方
- 扣减不超过 `from.troops`（clamp 保护）
- `amount` 单位为千（k），与现有兵力单位一致

#### 5.6.6 议和结算（接受后）

玩家点「接受」→ 按条件顺序执行 → 结束战斗：

```
1. 逐条件执行：
   cedeCity("汉中市")    → applyEvent({ type:'capture', targetGb, actor: opponent })
   cedeTroops("成都市",10) → applyEvent({ type:'transferTroops', fromGb, toGb: opponentCity, amount:10 })
2. 结束战斗：
   applyEvent({ type:'battleEnd', battleId, reason:'peace' })
3. 攻方 fieldForce 处理：
   reason='peace' 与 'retreat' 同逻辑——剩余 fieldForce 转回来源城 troops
4. Toast / 电报：
   "议和达成 · {narrative}"
```

**拒绝后**：什么都不做，战斗继续。可追加 Toast "议和破裂"。

#### 5.6.7 `BattleEndReason` 扩展

现有：`capture | attackerRouted | retreat | defenderCollapse | attackerCollapse`

新增：`peace`（议和停战）。reducer 中 `peace` 与 `retreat` 走同一分支（fieldForce 转回城），但额外执行条件事件。

#### 5.6.8 攻守双方求和的差异

| | 攻方求和 | 守方求和 |
|---|---|---|
| 语义 | "我不打了，放我走" | "我认输，请停手" |
| AI 裁定方 | 守方领袖 | 攻方领袖 |
| 条件方向 | 守方向攻方提条件 | 攻方向守方提条件 |
| 割城来源 | 攻方的城（前线占领的或本土的） | 守方的城（被围的或邻近的） |
| 让兵来源 | 攻方 fieldForce / 来源城 troops | 守方 troops |
| 典型场景 | 久攻不下、损失惨重 | 城防将破、援军无望 |

> 守方求和时，AI 裁定者是**攻方领袖**——攻方通常占主动，条件可能更苛刻。

#### 5.6.9 与撤退的关系

| | 撤退（已实现） | 议和（本设计） |
|---|---|---|
| 发起方 | 仅攻方 | 攻守双方 |
| 对方同意？ | 不需要（单方走人） | **需要** |
| 代价 | AI 裁定追击减员（不可拒绝） | AI 开条件（玩家可选接受/拒绝） |
| 拒绝后果 | — | 战斗继续 |
| 弹窗 | 裁决结果（只读，点"知晓"） | 条件协商（可接受/拒绝） |

#### 5.6.10 后续扩展

- **赔款**：国库系统落地后，新增 `reparations` 条件类型。
- **多轮谈判**：玩家拒绝后可还价（"割城不行，让兵 5k 如何？"），AI 再裁。v1 不做，一轮定成败。
- **AI 主动求和**：P3 阶段 AI 势力可发起议和，走同一裁定链路（角色互换）。
- **同盟斡旋**：第三方势力介入调停，降低条件苛刻度（外交系统联动）。

## 六、玩家交互模型

### 6.1 择势（开局选政权）

- 进入游戏，玩家从十大政权择一作为自己的势力。
- 选择结果驱动：地图"我方"高亮、敌我着色、玩家视角默认参数。
- 选择即写入玩家势力标识；未选时地图交互受限（无法下指令）。

### 6.2 指挥循环（玩家阶段 P1）

玩家**用自然语言指挥**，无需记忆指令语法：

1. 玩家在地图底部常驻面板输入意图（如"川军自重庆挥师东进，剑指杭州"）。
2. **玩家 AI**（兼任"军事参谋 + 战局推演者"）将意图翻译成游戏指令，并逐条判定可行性。
3. 经战略校验（只能为本势力决策、不能指挥他国、不能未战占领等）后，**自动入队并执行**，玩家无需手动点"推进"。
4. 玩家可在本回合内反复发送，形成战术组合。

> 玩家 AI 权限约束：只能为本势力决策；**严禁**直接操纵势力存亡/归属（`setFactionAlive`/`setCurrentFaction`）；**不控制日期**（日期由世界 AI 在结算时统一推进）。

### 6.3 指令词汇表（玩家 / AI 通用，共 17 条）

内核只接受以下结构化指令。分三类：**演出类**（不改世界态，纯表现）、**世界态类**（经内核确定性变更）、**查询/管理类**。

| # | 指令 | 类别 | 语义 |
|---|------|------|------|
| 1 | `arrowFly` | 演出 | 箭头弧线飞行动画（派兵/行军表现） |
| 2 | `radarPulse` | 演出 | 雷达脉冲扩散（侦察表现） |
| 3 | `orbBurst` | 演出 | 光球抛射 + 爆炸 + 震波（宣战表现） |
| 4 | `battle` | 世界态(登记) | 开启持续战斗，双向交火动画，登记战斗元数据（含攻守方） |
| 5 | `stopBattle` | 世界态 | 停止指定战斗（携带 reason：retreat/surrender） |
| 6 | `stopBattles` | 演出/管理 | 停止所有战斗 |
| 7 | `listBattles` | 查询 | 返回进行中战斗列表 |
| 8 | `fogCover` | 演出 | 全屏云雾蒙太奇（时间流逝表现） |
| 9 | `capture` | 世界态 | 占领/接收城市：易主 + 可选写入新驻军 |
| 10 | `moveTroops` | 世界态 | 调兵：从 A 城搬运 N 千兵到 B 城（from 扣、to 加） |
| 11 | `deploy` | 世界态 | 出兵：从来源城派出 N 千兵力（troops → fieldForce） |
| 12 | `reinforce` | 世界态 | 增援：向战斗中的前线补充 N 千兵力 |
| 13 | `recruit` | 世界态 | 征兵：城市驻军增加 |
| 14 | `setFactionAlive` | 世界态 | 设置势力存亡（alive=false = 灭亡，移出存活列表） |
| 15 | `setCurrentDate` | 世界态 | 推进全局日期（须放指令序列末尾，作为时间步收尾） |
| 16 | `setCurrentFaction` | 世界态 | 切换玩家操控势力（系统管理） |
| 17 | `develop`/`fortify`/`rally` | 世界态 | 内政：建设（工业/粮食）、筑防（工事）、整军（士气） |

- **地点参数**：所有地点填城市中文名即可（如"北京""上海"），系统自动解析为内部编码；兼容直接填编码。
- **玩家模式限制**：`capture` 需前置 `battle`，不得直接占领未开战城市；`setFactionAlive`/`setCurrentFaction` 对玩家禁用；`moveTroops` 仅限己方两城之间调兵。
- **战斗指令链**：`deploy`（出兵）→ `battle`（开战）→ 每回合 P4a 自动 `attack`（结算）→ `stopBattle`/守方归零（结束）。`reinforce` 可在战斗进行中随时下达。

### 6.4 战略可行性判定（三维度）

玩家 AI 对每条指令做可行性推演（0~5 分），作为"参谋建议"而非硬性锁死：

| 维度 | 权重 | 含义 |
|------|------|------|
| 地理可达性 | 0.4 | 行军路线多通畅？沿途多少敌对势力？有无天然屏障？0=完全不可达，5=邻接 |
| 兵力可行度 | 0.3 | 可调动力（驻军 + 可集结的邻城兵力）vs 防守方×地势加成？0=毫无胜算，5=明显优势 |
| 政治连锁 | 0.3 | 是否引发不可承受外交后果？0=自杀式挑衅，5=无关痛痒 |

**综合分 = 地理×0.4 + 兵力×0.3 + 政治×0.3**，三档：

- ✅ **feasible（可行）**：综合 ≥ 3.5，直接执行。
- ⚠ **difficult（困难）**：2.0~3.4，有障碍但非不可能，附前置步骤建议。
- ❌ **impossible（不可行）**：< 2.0 或存在不可逾越阻断，附替代方向。

> 示例：川军自成都攻汉中（相邻、驻军不多）→ feasible；自成都攻杭州（数千里、须击穿两道防线）→ impossible，建议先经营陕南走廊。

### 6.5 回合结构（四阶段 P1–P4，P4 拆两段）

整轮被拆为**玩家 AI（战术执行）+ 世界 AI（调度者 + 结算者）+ 政权 AI（决策执行者）**三层，边界清晰：

```
┌─ P1 玩家阶段 ──────────────┐
│ 玩家反复下指令；点「结束玩家回合」  │
└────────────┬────────────────┘
              │ 结束玩家回合（仅 P1→P2 边界，不推进日期）
              ▼
┌─ P2 世界AI·调度 ───────────┐
│ 向各政权AI发问询：「你是否要行动？」│
└────────────┬────────────────┘
              │ 问询已发
              ▼
┌─ P3 政权AI·决策执行 ───────┐
│ 各势力读世界态·决策·落地执行      │
│ （含战斗决策：增援/撤退/继续）    │
│ （「无动作」亦为合法回复）         │
└────────────┬────────────────┘
              │ 全部政权AI完成
              ▼
┌─ P4a 战斗裁决AI ───────────┐
│ 遍历所有 ACTIVE 战斗          │
│ 每场裁定本轮损耗 → attack 事件  │
│ 检查终止条件 → capture/battleEnd │
│ 无 ACTIVE 战斗时跳过（零调用）   │
└────────────┬────────────────┘
              │ 战斗结算完毕
              ▼
┌─ P4b 世界AI·结算 ──────────┐
│ 收集本轮事件（含战斗结果）       │
│ 生成叙事·电报·推进日期（新回合）  │
└────────────────────────────────┘
```

- **「结束玩家回合」只是 P1→P2 的玩家动作**，并不直接推进日期；日期推进发生在 P4b 结算之后。
- **P4a 战斗裁决 AI** 是独立调用（与 P4b 世界叙事分开），聚焦战斗裁定：输入所有 ACTIVE 战斗的紧凑摘要，输出每场的 `attackerLoss`/`defenderLoss`。无战斗时跳过，零成本。
- **P4b 世界 AI** 基于 P4a 的战斗结果写叙事文案、发电报、推进日期——战斗结果必须先于叙事产生，逻辑上就是两步。
- **世界 AI 不当"总导演"**，而是**校验者 + 叙事者**：检测非法/不合理指令并打回，并生成叙事文案。
- **政权 AI** 各自读世界态、决策、执行，与玩家同链路；"无动作"为合法回复。
- 结算（P4）必须在所有政权 AI 完成后才执行，二者是"先后"而非"跳过"。

#### 战斗中的每回合决策空间

| 决策 | 玩家怎么做 | AI 怎么做 |
|------|-----------|-----------|
| 继续打 | 什么都不做（战斗自动延续） | P3 不下 stopBattle |
| 增援 | P1 下 `reinforce` | P3 下 `reinforce` |
| 撤退 | P1 下 `stopBattle` | P3 下 `stopBattle` |
| 外交斡旋 | P1 发报求援/劝降 | P3 发报 |
| 投降/放弃 | `stopBattle` + `capture`（预留 surrender 语义） | 同上 |

> 战斗不是"开打后等结果"——每回合都有决策点，这是跨回合模型的核心游戏性。

## 七、AI 对手设计

> **落地进度说明**：以下为设计愿景，当前实现程度详见《引擎架构决策记录.md》§0 总览表。核心 P1–P4 四阶段流水线已部分落地（P1 玩家阶段 ✅、P2 分类/P3 决策/P4 结算 🟡）；规则 AI 兜底、快照瘦身、外交消息总线、多剧本等仍待实现（⬜）。

- **每主要势力配一个 AI 实例**，另设一个**世界 AI**（叙事事件 + 各势力操作汇总）和一个**战斗裁决 AI**（P4a，裁定战斗损耗）。
- **智能动态增减**：势力灭亡 → 移除其 AI；新势力崛起 → 新增 AI。
- **战斗裁决 AI（P4a，独立调用）**：每回合遍历所有 ACTIVE 战斗，输入紧凑摘要，输出每场损耗。详见 §5.2.3。
  - **输入格式**（每场战斗一行，约 100 token，10 场也就 1000 token）：
    ```
    ACTIVE: battle_3 KMT(奉天/fieldForce 12000/士气65) vs NEA(锦州/troops 8000/士气40) fort=3 terrain=城市 turns=3 lastTurn: atk-750 def-400 trend=攻方占优
    ```
  - **输出**：`{ resolutions: [{ battleId, attackerLoss, defenderLoss, narrative? }] }`
  - **参考区间**：prompt 里给损耗参考表（§5.2.3）防止 AI 给出离谱数字，但不写死公式——弱策略推演的叙事多样性是卖点。
  - **上限保护**：一批最多裁定 N 场（如 5 场），超出的延后到下回合。
  - **兜底**：AI 漏了某场战斗 / LLM 失败 → 跑 `fallbackTick`（§5.2.3），不卡死。
- **世界 AI 两类事件生产者**：
  1. **Agent‑Kernel（专属对话）**：仅限与玩家直接相关的阵营，走"玩家自然语言 → 世界AI校验路由 → 目标阵营AI回应 → 世界AI收口"的三段式外交。
  2. **世界 AI（一次性批量）**：其余阵营事件由世界 AI 据局势一次性生成带日期批次，不经逐阵营对话。
- **成本收敛**：平时每回合 1 次世界 AI 批量 + 1 次战斗裁决 AI（无战斗时跳过）+ 玩家相关对话 2~3 次；次要/小势力用**规则 AI 兜底**（如 `attackScore` 启发式），不调大模型。
- **快照瘦身**：别每步都喂全量城市，只喂"周边若干跳 + 与上帧差异"。
- 上述 AI 对手的编排与调度细节（调度器、`needsPlayerDecision` 停续、消息总线）见《引擎架构决策记录.md》。

## 八、视觉与表现

- **整体风格：羊皮纸水墨风**（与地图界面、择势弹窗一致）。主色：羊皮纸底（`--paper`）、墨色字（`--ink`）、朱砂红强调（`--cinnabar`）；通用 UI 组件统一前缀 `Game`。
- **地图渲染（Leaflet 底图 + PixiJS 动画叠加）**：
  - **Leaflet** 负责底图渲染、缩放平移、GeoJSON 要素加载、图层切换（中国省/市/县、世界地图）。
  - **PixiJS** 作为动画叠加层，承载所有演出效果：
    - 政权着色（10 色映射）、地名标签、图例面板。
    - 弧线派兵（黄点沿弧飞）、雷达扫描（绿圈扩散）、光球宣战（红光球 + 爆炸 + 震波）。
    - 持续交火战斗（两城双向发射光点循环，跨回合常驻直到战斗结算终止）。
    - **云雾蒙太奇**：全屏水墨云雾"盖屏 → 停顿 → 揭开"，作为"时间流逝"演出原语，在日期推进瞬间藏一次状态切换。
  - 相机控制由 Leaflet 提供，PixiJS 动画层与地图坐标同步。
- **兼容约束**：所有浮于地图之上的 UI 组件根元素须加 `map-ui` 类，使云雾演出时同步淡出，营造"整屏被雾吞没"的观感。

## 九、存档与剧本延续（设计层面）

- **事件溯源**：世界态是事件日志的纯函数结果。存档 = 序列化事件日志；读档 = 重放事件（不重跑 AI 裁定，保证确定性）。
- **多槽位 + 每回合自动存**：手动槽位供玩家存档；`auto` 槽在每次日期推进（回合边界）后自动写入，断点可续。
- **玩家身份随日志恢复**：择势事件本身进日志，读档重放时自动还原玩家势力，无需单独存。
- **战斗元数据进事件**：`battleStart`/`battleEnd` 携带的 `attacker`/`defender`/`turns`/`reason` 等全部在事件里，读档重放可完整重建战斗状态；PixiJS 动画句柄不进 store，读档后由 `restoreActiveAnimations` 重建。
- 设计上需保证：**新增世界态字段（如 `fieldForce`）必须同步纳入"开局重置清单"**，否则重复读档会累积脏数据（如战斗元数据未重置会翻倍、外出兵力残留）。

## 十、设计原则

1. **统一量纲**：全游戏尽量采用统一评分体系（cityLevel 1~5、industry/food 0~10、fort 0~5），方便 AI 权重计算。
2. **城市保存静态、动态交系统**：静态战略数据进城；部队/补给/士气波动/战斗状态由内核与事件维护。
3. **所有字段必须参与 AI 决策**：任一城市字段都应直接影响 AI 行为，否则该字段无设计价值。
4. **确定性优先**：攻城裁定结果写进事件，确保 replay 安全、存档可重放。
5. **AI 只产出意图**：AI 不直接改世界，世界态只经内核按事件变更（单一写者）。
6. **表现与状态解耦**：动画是状态变更的副作用，可从演出原语独立组合。
7. **兵随人走、城空可偷**：驻军与外出兵力分离（`troops`/`fieldForce`），出兵即离城、城空即可被偷家——所有战斗后果都是数据结构的自然推论，不堆特殊规则。
8. **弱策略、强叙事**：战斗由 AI 裁定而非确定性公式，同一局面可有不同走向；参考区间只防离谱，不扼杀多样性。

## 十一、后续扩展方向

未来版本可增加，但**新增字段必须能直接参与 AI 计算**，否则不建议加入：

| 方向 | 说明 |
|------|------|
| 铁路 / 机场 / 港口 | 影响行军速度与战略投放 |
| 特殊资源 `resource` | 战略物资约束 |
| 人口 `population` | 征兵上限与恢复 |
| 文化 `culture` / 稳定度 `stability` / 抵抗度 `resistance` | 治理与沦陷区管理 |
| **投降语义 `surrender`** | 当前用 `stopBattle`+`capture` 两步表达，后期可独立成语义（含"不战而降"叙事） |
| **议和系统** | 战斗中参战方可发起议和，AI 裁定条件（割城/让兵/赔款），详见 §5.6 |
| **多路出击** | 当前一城只能作为一个方向的攻方来源；后期可支持 `fieldForce` 分兵多路 |
| **将军倒戈 / 无主之军** | 来源城被占后，外出兵力当前直接溃散；后期可让 AI 决定投降/投奔友军/继续打 |
| **补给系统** | v1 暂不加；后置以更真实表达远程奔袭 |
| **规则 AI 兜底** | 次要势力 `attackScore` 启发式，收敛大模型成本 |
| **快照瘦身** | 周边若干跳 + 帧间差异，砍 token |
| **外交消息总线** | 跨阵营三段式对话（玩家→世界AI→目标AI→世界AI收口） |
| **世界 AI 批量事件** | 非玩家相关阵营一次性生成带日期事件批次 |
| **多剧本** | 1931/1937/1941/1945 开局种子与平衡 |
