## 1. 设计目标与原则

旧设计的隐藏问题：**减员数字全由 AI 拍板**，导致调平衡 = 改 prompt 求 LLM 听话（又玄学又贵）、AI 超时则战斗瘫痪、replay 时 AI 重问结果发散。

重构后确立四条底线：

1. **公式主干 + AI 调味**：基础减员由本地确定性公式计算；AI 只作为「战地记者」追加突发减员（shock）与士气扰动（morale），且产出被系统性钳制。
2. **AI 不判胜负**：终局（谁胜谁负、是否崩溃）由系统侧确定性规则检查，AI 不碰。延续架构铁律「AI 不判胜负、终局由系统检查」，升级为「AI 只调味、主干公式定、终局规则判」。
3. **replay 安全**：所有随机性（士气崩溃判定）使用 `battleId + turns` 的状态哈希（FNV-1a），不依赖 `Math.random()`；AI 调味结果合并进 `attack` / `moraleChange` / `narrative` 事件落入事件日志，replay 重放的是既成事实，不重新问 AI。
4. **AI 失败无感降级**：调味层 `try/catch` 包裹，调用失败直接用纯公式结果结算，玩家无感知。

## 2. 核心数据模型

### 2.1 CityState（与战斗相关字段）

| 字段 | 含义 | 战斗中的角色 |
|---|---|---|
| `troops` | 驻军（k） | 守方兵力；`attack` 事件扣减它 |
| `fieldForce` | 外出兵力（k） | 攻方兵力；`attack` 事件扣减它；`capture` 后入城 |
| `morale` | 士气 0–100 | 公式参数 + 崩溃判定轴 |
| `fort` | 工事 0–100 | 攻损率乘数 |
| `terrain` | 地形 | `mountain`/`hill`/`plain` → 攻损率乘数 |
| `owner` | 归属势力 | 偷家检测、战败判定依据 |

### 2.2 BattleInfo（战斗记录）

| 字段 | 含义 |
|---|---|
| `id` / `from` / `to` | 战斗编号 / 攻方来源城 / 守方目标城 |
| `attacker` / `defender` | 交战双方势力代码 |
| `fromName` / `toName` | 中文城名 |
| `active` | 是否进行中（结算与否依据） |
| `turns` | 已打回合数（`attack` 时 `++`） |
| `totalAttackerLoss` / `totalDefenderLoss` | 累计损耗（趋势判断） |
| `lastAttackerLoss` / `lastDefenderLoss` | 上回合损耗（摘要展示） |
| `lastNarrative` | 最近一份战报文案 |

### 2.3 事件流

```
battleStart     → 创建 BattleInfo（active=true）
   ── 每回合结算 ──
   attack           → 扣攻方 fieldForce + 守方 troops，更新累计统计，回合数+1
   moraleChange ×N  → 公式士气损耗 + AI 士气扰动（顺序叠加）
   ── 终局 ──
   capture + battleEnd('capture' | 'defenderCollapse') → 守方城易主
   battleEnd('attackerRouted' | 'attackerCollapse' | 'retreat') → 攻方退场
```

> 注意：**`battleEnd` 事件本身不改变城市态**（apture 由独立的 `capture` 事件承担），它只负责清理 `BattleInfo` 与攻方来源城的 `fieldForce`（见 §6）。

## 3. 战斗结算时序（P4a）

玩家点「结束回合」→ `runWorldTurn()` → P3 政权 AI 演出 → **★ P4a `settleActiveBattles()` ★** → P4b 日期推进。

```
玩家点「结束回合」
        │
        ▼
runWorldTurn()
  ├─ P3  政权 AI 演出（逐势力对话 / 世界 AI 批量事件）
  ├─ ★ P4a settleActiveBattles() ★        ← 本文档主角
  │     ├─ ① 前置检查 + computeBaseBattle()（算好，暂不展示）
  │     ├─ ② await callLlm 战地记者调味（try/catch：失败则纯公式走人）
  │     ├─ ③ clampFlavor 钳制 + 合并 → applyEvent(attack / moraleChange)
  │     └─ ④ 终局复检（士气崩溃优先 → 兵力归零兜底）
  └─ P4b 日期推进（云雾蒙太奇 + dateAdvance）
```

**三处关键设计**：

- **先算后喂、一并展示**（② 在 ①③ 之间）：AI 调味时能看到公式已算出的基础减员，「解释」而非「覆盖」战局，且玩家只看到一次完整战报。
- **多场战斗一次 AI 调用**：所有 active 战斗的 base 结果打包进一个 prompt，AI 一次返回全部调味，省调用次数、降延迟。
- **降级路径**：② 失败 → `flavorMap` 保持空 → ③ 直接用 base 结算，核心循环不阻塞。

## 4. 基础减员公式（核心）

定义在 `utils/battleFormula.ts` 的 `computeBaseBattle()`，**纯函数、无 Vue 依赖、可单测**。

### 4.1 输入

```ts
interface BattleInput {
  atkForce: number      // 攻方外出兵力
  defTroops: number     // 守方驻军
  atkMorale: number     // 攻方士气
  defMorale: number     // 守方士气
  fort: number          // 守方工事 0–100
  terrain?: string      // 守方地形 mountain/hill/plain
  distanceFactor?: number // 远征战力衰减系数（默认 1.0，无衰减）
}
```

### 4.2 中间系数

```
ratio        = clamp(atkForce / defTroops, 0.5, 3.0)          // 兵力比，封顶 0.5~3.0
fortFactorRaw = fort <= FORT_CURVE_SEED                      // 工事曲线：种子基准(20)以下线性，之上 sqrt 凹曲线
  ? fort / 100
  : FORT_CURVE_SEED/100 + (1 − FORT_CURVE_SEED/100) × sqrt((fort − FORT_CURVE_SEED)/(100 − FORT_CURVE_SEED))
fortFactor   = 1 + fortFactorRaw × (2.0 − 1)                  // fort=0→1.0，fort=20→1.2（种子不变），fort=100→2.0
terrainFactor = { mountain: 1.5, hill: 1.2, plain: 1.0 }[terrain]
moraleFactor(m) = clamp( 1 + (70 − m) / 100 , 0.7 , 1.6 )     // 士气参考线 70
```

> **工事只影响守方损耗（守损率分母），不影响攻方损耗**——fort 是守方减伤乘数，不是攻损乘数（早期文档写反过）。
> 凹曲线目的：防“刷数字”——种子 fort=20 的 351 城开局防御不变，玩家 fortify 从 20 往上堆时边际收益递减（甜点区约 40）。

`moraleFactor` 速查：

| 士气 m | 算式 | 损耗乘数 |
|---|---|---|
| 100 | clamp(0.7) | **0.7**（满士气，损耗最低） |
| 70 | 1.0 | 1.0（参考线） |
| 40 | 1.3 | 1.3 |
| 20 | 1.5 | 1.5 |
| 0 | clamp(1.7→1.6) | **1.6**（崩溃边缘，损耗最高） |

### 4.3 损耗率与取整

```
攻损率 = baseRate × terrainFactor × moraleFactor(atkMorale)
守损率 = baseRate × ratio / fortFactor × moraleFactor(defMorale)

attackerLoss = max(1, round(atkForce × 攻损率))
defenderLoss = max(1, round(defTroops × 守损率))
```

`baseRate = 0.08`（每回合基准损耗率，集中配置可调）。`max(1, …)` 保底——不出现 0 损耗（除非被 AI 调味负向覆盖，但钳制后合并仍 `max(1, …)`）。

### 4.4 士气联动（公式自带，非 AI）

每损失 10% 兵力 → 士气 −3：

```
moraleDeltaFromLoss(lossRate) = −round( lossRate × 100 / 10 × 3 )
```

`computeBaseBattle` 返回的损失率（`attackerLoss / atkForce`）直接换算出 `atkMoraleDelta` / `defMoraleDelta`，作为 `moraleChange` 事件写入。

> **为什么重要**：在旧设计里士气是「死数字」，只被 AI 当作算损耗的参考，没有任何后果。重构后士气既是公式参数（影响损耗速率），又通过本联动持续下滑、累积触发 §6.1 的崩溃判定——一条被激活的战略轴。

### 4.5 远征战力衰减（距离因子）

远征军长途跋涉，战斗力随距离下降。衰减系数量化的是**攻方有效兵力**，不改变守方。

```
effectiveAtk = atkForce × distanceFactor

distanceFactor = max(EXPEDITION_DECAY_FLOOR, 1 − distance / EXPEDITION_DECAY_REF_KM)
```

| 行进距离 | 因子 | 效果 |
|---|---|---|
| 200 km 内 | ≈ 0.9 | 几乎无影响 |
| 800 km | 0.6 | 远征军战力打六折 |
| 1200 km+ | 0.4（封底） | 远征军最多打四折 |

常量定义在 `utils/economy.ts`：
- `EXPEDITION_DECAY_REF_KM = 2000`：参考距离，2000 km 时因子逼近 0（但被下限兜底）
- `EXPEDITION_DECAY_FLOOR = 0.4`：衰减下限

**对 ratio 的影响**：`ratio = clamp(effectiveAtk / defTroops, 0.5, 3.0)`。远征军兵力打折后，ratio 降低 → 守方损耗降低，实现"远征军打不动坚城"的战略纵深。

### 4.6 示例计算

**例 A｜攻守相当、双方士气 70、无工事、平原**

```
atkForce=100, defTroops=100, atkMorale=70, defMorale=70, fort=0, terrain=plain
ratio=1.0, fortFactor=1.0, terrainF=1.0, moraleFactor(70)=1.0
攻损率 = 0.08×1×1 = 0.08 → attackerLoss = round(100×0.08) = 8
守损率 = 0.08×1.0/1.0×1.0 = 0.08 → defenderLoss = round(100×0.08) = 8
士气：8/100=8% 损失 → −round(0.8×3)=−2（双方各 −2）
```

**例 B｜攻方 3 倍、满士气；守方士气 50、工事满、山地**

```
atkForce=300, defTroops=100, atkMorale=100, defMorale=50, fort=100, terrain=mountain
ratio=clamp(3.0)=3.0, fortFactor=2.0, terrainF=1.5, moraleFactor(100)=0.7, moraleFactor(50)=1.2
攻损率 = 0.08×1.5×0.7 = 0.084 → attackerLoss = round(300×0.084) = 25
守损率 = 0.08×3.0/2.0×1.2 = 0.144 → defenderLoss = round(100×0.144) = 14
```

> 手感校验：攻方三倍且满士气，损 ~8%（山地加重攻损，但满士气抵消）；守方损 14%（工事满减伤近半）。符合「优势方速推、守方坚城拖延」的预期。

**例 C｜守方士气 10（崩溃边缘）**

```
仅看士气乘数：moraleFactor(10) = 1.6，比士气 70 时（1.0）损耗速率高 60%
→ 低士气防守方会更快被打崩，更易触发 §6.1 崩溃
```

## 5. AI 调味层（战地记者）

定义在 `aiPromptBuilder.ts`（`buildBattleFlavorPrompt` + `buildBattleFlavorSummary`），由 `utils/battleFormula.ts` 的 `clampFlavor` 钳制。

### 5.1 角色

AI 是「战地记者」：**为战报增添戏剧色彩，而非改变战局**。它看到公式已算出的基础减员，可追加两类可选事件：

| 事件 | 字段 | 含义 | 系统钳制 |
|---|---|---|---|
| `shock` | `side` + `magnitude`(k) + `narrative` | 突发减员（弹药库殉爆、主将阵亡、伏兵突袭） | `magnitude` 封顶 `round(baseLoss × 0.5)`，且 >0 才保留 |
| `morale` | `side` + `delta` + `narrative` | 士气扰动（援军、瘟疫、哗变、捷报） | `delta` 封顶 `±20` |

`shock` 直接加进对应方的本轮减员：`finalLoss = base + shock`（再 clamp 到该方现有兵力）。`morale` 作为独立的 `moraleChange` 事件叠加在公式士气损耗之后。

### 5.2 稀缺度原则（prompt 引导，无硬配额）

> - 大多数回合 `events` 应为空数组 `[]`——「什么都没发生」才是战场常态。
> - 突发事件是**稀缺的戏剧高潮**，不要每回合都输出；一场战斗里出现一两次 `shock` 已足够。
> - 你本轮确实没有值得报告的突发，直接返回空 `events`，**不要硬编**。
> - 你不需要判定谁胜谁负——终局由系统检查。

> 注：用户拍板**不引入**每场战斗的累计配额硬闸，仅用 prompt 约束稀缺度。AI 若抽风每回合都编，`clampFlavor` 的封顶仍保证它无法「改命」（shock 最多基础减员的 50%，morale 最多 ±20）。

### 5.3 钳制实现（clampFlavor）

```ts
shock   → magnitude = clamp(round(magnitude), 0, round(baseLoss × 0.5))  // 且 >0 才保留
morale  → delta = clamp(round(delta), −20, +20)
非法 type → 直接丢弃
```

合并顺序（`useGameScheduler` 第三阶段）：

```
finalAttackerLoss = min( max(1, base.attackerLoss + Σshock(attacker)) , from.fieldForce )
finalDefenderLoss = min( max(1, base.defenderLoss + Σshock(defender)) , to.troops )
```

### 5.4 失败降级

```ts
try { /* await callLlm → 解析 results[] → flavorMap */ }
catch { /* console.warn，flavorMap 保持 {} → 纯公式结算 */ }
```

## 6. 终局判定（胜负条件）

**核心事实**：当前没有「达成某条件即判胜」的硬规则。胜负由以下**确定性系统判定**自然产生——AI 不判。优先级：**士气崩溃 > 兵力归零 > 异常终止**。

### 6.1 士气崩溃（checkMoraleCollapse）✅ 已实现

定义在 `battleFormula.ts`，确定性伪随机、replay 安全。

**触发前提**：任一方 `morale ≤ 20`（>20 直接不崩）。

**崩溃概率**（线性插值）：

```
collapseRate(m) = m > 20 ? 0 : min(1, 0.4 + (1 − m/20) × 0.6)
```

| 士气 m | 崩溃概率 |
|---|---|
| 20 | 0.40 |
| 15 | 0.55 |
| 10 | 0.70 |
| 5 | 0.85 |
| 0 | 1.00 |

**确定性判定**（不依赖 `Math.random`）：

```ts
seededChance(seed) = (FNV-1a(battleId|turns|side) >>> 0) % 1000 / 1000   // ∈ [0, 1)
if (rate > 0 && seededChance(seed) < rate) → 该方崩溃
```

- **守方优先判定**（攻城方天然吃亏：同概率下先判守方崩）。
- 种子含 `turns`，每回合不同 → 同一场战斗逐回合独立抽样，但 replay 时结果完全可复现。

**崩溃结果**：

| 崩溃方 | 事件序列 | 结局 |
|---|---|---|
| 守方 `defenderCollapse` | 先 `capture`（resultTroops = 攻方剩余 `fieldForce` 入城）→ 再 `battleEnd('defenderCollapse')` | 守方城陷，攻方胜 |
| 攻方 `attackerCollapse` | 仅 `battleEnd('attackerCollapse')` | 攻方溃散，守方胜 |

`battleEnd` reducer（game.ts L486）把 `defenderCollapse` / `attackerCollapse` 与 `capture` / `attackerRouted` 并入同一分支 `from.fieldForce = 0`（攻方来源城清空外出兵力）。`defenderCollapse` 不丢兵：capture 已先把攻方剩余兵力写进被占城 `troops`，再清 source 的 `fieldForce`。

### 6.2 兵力归零（原逻辑保留）✅ 已实现

终局复检第二顺位（仅在未触发崩溃时）：

| 条件 | 事件 | 结局 |
|---|---|---|
| 守方 `to.troops ≤ 0` | `capture` + `battleEnd('capture')` | 守方城陷 |
| 攻方 `from.fieldForce ≤ 0` | `battleEnd('attackerRouted')` | 攻方溃败（兵锋耗尽） |

### 6.3 异常终止（前置/兜底）✅ 已实现

| 时机 | 条件 | 事件 | 说明 |
|---|---|---|---|
| 开打前 | 攻方来源城已被第三方占领 | `battleEnd('attackerRouted')` | 偷家，前线自溃 |
| 开打前 | 攻方来源城 `fieldForce ≤ 0` | `battleEnd('retreat')` | 无兵，温和撤销（兵转回驻军） |
| 开打前 | 守方 `troops ≤ 0` | `capture` + `battleEnd('capture')` | 无仗可打，直接易主 |

### 6.4 BattleEndReason 枚举

```ts
type BattleEndReason =
  | 'capture'            // 守方兵力归零 / 守方崩溃 → 城陷
  | 'attackerRouted'     // 攻方兵力归零 / 偷家 / 兵锋耗尽
  | 'retreat'            // 无兵对峙，温和撤销（兵回城）
  | 'defenderCollapse'   // 守方士气崩溃（≥ v1 新增）
  | 'attackerCollapse'   // 攻方士气崩溃（≥ v1 新增）
```

### 6.5 单场战斗的败方下场（设计稿 · 待定参）

> 当前实现有一个重大缺口：两城交战的「战败」只有全灭一种结局——攻方溃败 `fieldForce` 直接归零、守方城破守军凭空消失。没有「打败但不全灭」的中间层次。以下为已定方向、参数待确认的设计。

#### 缺口分析

| 当前结局 | 败方下场 | 问题 |
|---|---|---|
| `attackerRouted` / `attackerCollapse` | `fieldForce = 0`，兵全没 | 剩 1 个兵和剩 100 个兵下场一样，无「止损撤退」的空间 |
| `capture` / `defenderCollapse` | 守军无交代，凭空消失 | 被歼？被俘？溃散？叙事不成立 |
| 无论哪种 | **胜方零收益** | 打赢没有士气提振/战利品/威慑连锁，进攻动力不足 |

#### 设计（① + ② 为必做）

| # | 设计 | 规则 | 改动位置 |
|---|---|---|---|
| ① | **溃败保留残部** | `attackerRouted` / `attackerCollapse` 发生时，`fieldForce` 不清零，而是按比例 `R`（建议 30–50%）转为来源城 `troops`（残部逃回），同时来源城士气再 `−10`。剩余部分散失 | 改 `battleEnd` reducer（game.ts L486）的 `attackerRouted` / `attackerCollapse` 分支 |
| ② | **胜方士气提振** | 攻方胜利（capture）→ 攻方来源城 `morale +10`。守方胜利（attackerRouted / attackerCollapse）→ 守方 `morale +5`，败方周边友城 `morale −5`（威慑扩散） | `settleActiveBattles` 第四阶段，终局复检后追加 `moraleChange` 事件 |
| ③ | 败方士气的进一步打击 | 战败后再砍士气：以 `−10`（失去辎重、溃散恐慌）叠加在公式士气损耗之上 | 同①的 apply 处 |

## 7. 战败判定与城市交接（设计稿 · 待实现）

> 当前版本**没有自动战败判定**。`setFactionAlive(faction, false)`（势力覆灭）事件存在，但被划为「仅世界 AI 可用」——一个势力被打下最后一座城后，系统不会自动判它死，需世界 AI 记得发指令，不可靠。以下为已拍板、待落地的设计。

### 7.1 战败条件

> **一个势力名下 0 座城 → 覆灭。**

城是唯一的生产资料；0 城 = 失去立足之地 = 政权不存在。残余野战军失去根据地，溃散。

### 7.2 判定时机：回合末统一对账

不在每次 `capture` 即时判（一回合可能连下数城），而是 **P4a 全部结算完成后、P4b 日期推进前**，统一扫一遍：

```
runWorldTurn: P3 → P4a 战斗结算 → ★ auditFactionSurvival() ★ → P4b 日期推进
```

新增 `auditFactionSurvival()`（导出，供 `useAgentKernel.runWorldTurn` 调用）。

### 7.3 覆灭时触发三件事

| # | 动作 | 说明 |
|---|---|---|
| ① | `setFactionAlive(faction, false)` | 从 `activeFactions` 移除；地图/电报/AI 调度全部生效 |
| ② | 强制结束该势力所有战斗 | 攻方身份 → `attackerRouted`（兵散）；守方身份 → `capture`（城已陷） |
| ③ | Toast 播报「XX 势力覆灭」 | 给玩家明确反馈 |

**城市不需要「批量交接」**——城是一座座被 `capture` 打下来的，到 0 城时早已全部易主，不存在整批转让。

### 7.4 连带修复：capture 应清 fieldForce（待实现）

当前 `capture` reducer（game.ts L541）只改 `owner` / `troops`，**不清 `fieldForce`**。若被占城同时是另一场战斗的攻方来源城（它有外出的 `fieldForce`），城陷后这部分兵力会变成「孤儿」挂在别人城里。设计补一行：

```ts
case 'capture':
  t.owner = e.actor
  t.fieldForce = 0          // 新增：城陷，原外出兵力失去根据地
  if (e.resultTroops != null) t.troops = Math.max(0, e.resultTroops)
  break
```

### 7.5 边界情况

| 情况 | 处理 |
|---|---|
| 覆灭势力有野战军在外 | ② 的 `battleEnd` 清 `fieldForce`；无战斗的孤儿兵力由 §7.4 修复 |
| 一回合连下 N 城致覆灭 | 统一对账只判一次，不重复 |
| 玩家覆灭 | 设 `gameOver` 标志 + Toast；完整结算界面另期做 |
| NEUTRAL 无主城池 | 跳过，不在 `activeFactions` 内 |
